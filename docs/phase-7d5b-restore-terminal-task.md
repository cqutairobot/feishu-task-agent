# Phase 7D-5B：恢复误操作终态任务

状态：已完成实现与自动化校验，等待两项真实管理后台验收。

## 目标

管理员误点“标记完成”或“取消任务”后，可以在同一群的管理后台恢复任务，避免
误操作让任务永久停在终态。恢复不是删除或覆盖历史，而是新增一条独立的
`restore` 生命周期事件。

## 业务规则

- 只有任务所属 `chat_id` 的当前管理员可以恢复。
- 只有 `done` 和 `cancelled` 任务显示恢复入口；`todo`、`overdue`、`pending`
  和已撤销任务不能恢复。
- 浏览器先显示二次确认，确认内容包含“原完成或取消审计保留”和“按当前截止时间
  重建提醒”。
- 截止时间为空或大于恢复时间时，状态恢复为 `todo`；截止时间已经到达或过去时，
  状态恢复为 `overdue`。
- 恢复会清空 `completed_at` 与 `cancelled_at`，但不修改原任务标题、说明、负责人、
  来源消息或证据。
- 恢复在同一事务中取消旧的未发送提醒并按当前状态重建提醒：未来截止时间生成
  72 小时、24 小时、当天和逾期四类提醒；已经逾期只生成逾期提醒；没有截止时间
  不生成四阶段提醒，继续使用缺失截止日期策略。
- 恢复事件触发私聊通知：每位负责人收到恢复通知，其他本群管理员收到管理员通知；
  操作人不会收到自己的重复通知，多角色收件人只收到一条。

## 审计与幂等

迁移 `20260824_0024` 扩展生命周期事件约束，允许 `restore`，并要求其前一状态为
`done` 或 `cancelled`、新状态为 `todo` 或 `overdue`。`task_notifications` 新增
`task_restored_coassignee` 和 `task_restored_admin` 两种通知类型。

管理后台请求使用浏览器生成的 `request_id`。相同请求 ID、任务、管理员、群和动作
会返回第一次结果，不重复写事件、提醒或通知；同一请求 ID 携带不同动作或任务会被
拒绝。原 `complete`、`cancel` 或 `invalidate` 事件不会被删除。

`restore` 不属于模型生命周期动作集合，也不接受普通私聊自然语言或任务卡片回调，
从权限边界上只允许管理后台管理员执行。

## 真实验收

真实验收只做以下两项，均在同一个已授权群的管理后台完成：

### A. 恢复已完成任务

1. 打开一个有未来截止时间的开放任务，点击“标记完成”。
2. 关闭并重新打开任务详情，点击“恢复为开放任务”，确认二次提示。
3. 检查任务状态为 `todo`，原 `complete` 审计仍在，并新增一条 `restore` 审计。
4. 检查未来截止时间的四条提醒已重新排期，负责人和其他管理员收到恢复私聊。
5. 重复刷新或重复提交同一请求不会产生第二条 `restore` 事件或重复通知。

### B. 恢复已取消且已逾期任务

1. 准备一个截止时间已过去的开放任务，点击“取消任务”。
2. 重新打开详情，点击“恢复为开放任务”，确认二次提示。
3. 检查任务状态为 `overdue`，原 `cancel` 审计仍在，并新增一条 `restore` 审计。
4. 检查只重新生成逾期提醒，不生成 72 小时、24 小时或当天提醒。
5. 检查负责人和其他管理员收到恢复私聊，且不会收到操作人自己的重复消息。

两项均确认符合后，才将本阶段标记为完成并进入 Phase 7D-5C（重复任务合并）。
