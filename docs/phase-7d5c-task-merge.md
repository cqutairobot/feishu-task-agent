# Phase 7D-5C：重复任务合并

状态：已完成实现与自动化校验，等待真实管理后台验收。

## 目标

当同一个群因为重复识别或管理员补建产生两条相同任务时，管理员可以保留一个正式
任务编号，把另一条任务合并进去。合并不会物理删除来源任务，也不会让负责人继续
收到两套提醒。

## 业务规则

- 只有来源任务所属群的当前管理员可以操作，服务端重新核验会话和群成员。
- 来源任务可以是 `pending`、`todo`、`overdue` 或 `done`；`cancelled`、已合并任务
  不提供合并入口。
- 保留目标必须属于同一个 `chat_id`，不能是来源任务自身、`cancelled` 或已合并任务。
- 合并后来源任务数据库状态为 `cancelled`，并设置 `merged_into_task_id` 和
  `merged_at`；管理读模型显示为 `merged` / “已合并”。
- 来源任务的证据消息和检测来源转移到保留任务；相同证据或检测来源只保留一份。
- 来源任务所有未发送提醒和负责人新任务通知都会取消，原因是 `task_merged`。
- 保留任务的编号、负责人、截止日期和当前状态不改变。

## 审计与幂等

迁移 `20260824_0025` 新增 `tasks.merged_into_task_id`、`tasks.merged_at`、合并目标
索引，以及 `task_lifecycle_events.merge_target_task_id`。合并写入独立 `merge`
生命周期事件，原任务的创建、完成、取消和其他审计永久保留。

管理后台请求必须携带 `request_id`。同一管理员、群、来源任务和请求 ID 重放时返回
第一次结果，不重复迁移证据、取消通知或写审计；同一请求 ID 改变动作、任务或合并
目标会被拒绝。LLM、普通私聊生命周期命令和任务卡片不接受 `merge`。

通知同步只推进 `merge` 生命周期游标，不为合并动作再创建一条状态通知，因为来源任务
的通知已经在合并事务内取消。

## 自动化校验

- 合并状态、证据与检测来源转移、提醒取消、请求幂等和跨群拒绝测试通过。
- 目标为已取消任务、来源为已取消任务的边界测试通过。
- 管理 HTTP 合并接口和数据库迁移 schema 测试通过。
- 通知同步跳过合并事件但推进游标测试通过。
- 管理前端 lint、生产构建和渲染契约测试通过。

## 真实验收

在一个已授权群的管理后台准备两条标题和内容明显重复的任务：

1. 打开重复任务 A，在“合并重复任务”下选择任务 B 作为保留任务并确认。
2. A 应显示“已合并”，并显示“保留任务：B 的编号”；A 的编号仍可在审计中查看。
3. B 的状态、负责人、截止时间和编号保持不变。
4. A 的未发送提醒和负责人新任务通知应取消，A 的证据与检测来源应出现在 B 详情中。
5. A 的生命周期中应新增 `merge`，原创建和其他历史事件仍保留；刷新或重复提交不能
   产生第二条合并事件。
6. 尝试选择已取消任务或跨群任务作为目标时，页面不提供该选项，服务端也返回冲突。

真实验收通过后，再开始 Phase 7D-6 的任务编号搜索与服务端分页。
