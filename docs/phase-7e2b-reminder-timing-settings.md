# Phase 7E-2B：每群自定义提醒时间

## 范围

当前群管理员可以调整现有四个负责人提醒阶段的时间：

- 第一提醒：截止前 `2..720` 小时，默认 72 小时。
- 第二提醒：截止前 `1..719` 小时，默认 24 小时。
- 截止当天：北京时间 `0..23` 时整，默认 09:00；若当天提醒时间晚于截止时间，
  则在截止时提醒。
- 逾期提醒：截止后 `0..1440` 分钟，默认 1 分钟。

第一提醒必须早于第二提醒，即第一提醒的提前小时数必须大于第二提醒。关闭某阶段
时，对应时间输入不可修改，但原设置值会保留。

## 数据与安全规则

- 迁移 `20260824_0028` 在 `chat_settings` 增加四个整数时间字段。
- 设置读取、修改、审计和提醒重算继续按精确 `chat_id` 隔离。
- 管理 API 同时执行类型、范围和两个提前量顺序校验；布尔值不能冒充整数。
- 保存设置时，同一事务重算本群开放任务的未发送提醒。
- 调整时间复用原提醒记录并修改 `scheduled_for`、`available_at`，不创建第二套记录。
- 已发送提醒保持终态，不因时间修改而重发。
- 被关闭阶段的时间值可以保存但不会进入实际提醒计划；重新开启后使用保存的值。
- 提醒私聊正文读取该条提醒的实际计划时间，不再硬编码“72 小时/24 小时”；例如
  自定义第二提醒为 36 小时时显示“第二提醒（截止前 36 小时）”。

## 自动化结果

- 默认值、合法更新、审计、非法范围、非法顺序和跨群隔离均已覆盖。
- 四个自定义时间的纯计算与真实持久提醒重排均已覆盖。
- 管理 HTTP API 和前端字段契约已覆盖。
- 完整 Python 回归 442 项通过；管理前端 lint、生产构建和 2 项页面契约测试通过。

## 真实验收

### 页面和群隔离

1. 进入群 A 的“群设置”。
2. 把第一提醒改为 96 小时、第二提醒改为 36 小时、截止当天改为 08 时、逾期后
   改为 15 分钟并保存。
3. 刷新后确认四个值保持，设置审计显示新时间。
4. 关闭第一提醒，确认第一提醒时间输入被锁定；重新开启后可修改。
5. 尝试把第一提醒改为 24、第二提醒改为 48，页面应提示“第一提醒必须早于第二
   提醒”并禁止保存。
6. 切换群 B，确认群 B 仍保留自己的默认值或既有值。

### 实际提醒重排（可选但推荐）

1. 在群 A 设置第一提醒为 48 小时、第二提醒为 24 小时并保存。
2. 创建一项截止时间约为当前时间后 60 小时的测试任务；负责人只应先收到新任务
   通知，第一提醒尚未到时。
3. 把第一提醒改为 72 小时并保存。新的第一提醒时间已进入过去，Reminder Worker
   应很快发送一次第一提醒。
4. 再次保存相同设置不会重复发送。

验收后取消测试任务，并把时间恢复到实际希望使用的策略。
